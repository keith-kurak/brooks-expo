## Linked Literate Programming (LLP)

This project uses **Linked Literate Programming**. Start with
[LLP 0000](./llp/0000-brooks.explainer.md) before making substantial changes.

- LLP documents live in `llp/` and use the filename convention
  `NNNN-slug.type.md`. Numbers are globally unique and never reused.
- New LLPs include `Type`, `Status`, `Systems`, `Author`, and `Date` metadata.
  Use `Role: Root` only for the corpus entry point.
- LLPs are living documents. Update them with the code and clearly mark stale
  guidance as `Superseded` or `Tombstoned`.
- Prefer extending an existing LLP when it already covers the topic.

## References

- Add an `@ref` when code implements a non-obvious decision documented in an
  LLP: `// @ref LLP NNNN#section — short gloss`.
- Read and verify an existing `@ref` before changing the code it governs.
- Do not annotate mechanically; a reference should add rationale that the code
  and filename do not already reveal.

## Working on Brooks

- Capture non-obvious design decisions while their rationale is fresh.
- Read the AI-agent development diary requirements in LLP 0000. For every
  substantial implementation or research task, add an entry under `diaries/`
  using `diaries/README.md`. Record useful successes, blockers, unexpected
  difficulty, comparative friction, evidence, and improvement ideas.
- Keep generated rationale tagged as `[observed]`, `[confirmed]`, or
  `[inferred]`; do not promote inferred claims without human confirmation.
- Land LLP updates in the same change as the implementation they explain.
- **Read LLP 0002 before touching anything in `src/data/` or
  `packages/catalog/`** — brooksrunning.com is behind Akamai Bot Manager and
  the data architecture follows from that.
- `packages/catalog` is the source of truth; the copies in `src/data/` and
  `assets/catalog.json` are generated by `bun run sync`. Edit the package, not
  the copies.

## Expo commands: use the Expo Agent CLI

Favor `npx @expo/agent-cli` (https://github.com/expo/expo-agent-cli) over
plain `expo`, `expo-doctor`, and `tsc` commands. It prints a plan, uses exit
codes you can branch on (0 ok, 1 bad command, 7 needs a human, 20 failed,
22 inconclusive), and has `--json` on every report. `npx @expo/agent-cli
help workflow` explains the loop.

| Task | Command |
| --- | --- |
| What the project is, what to run next | `npx @expo/agent-cli status` |
| Add a package at the SDK's version | `npx @expo/agent-cli install <pkg>` |
| Type check | `npx @expo/agent-cli typecheck` |
| Setup problems | `npx @expo/agent-cli doctor` |
| Dev server (Metro) | `npx @expo/agent-cli start -- <expo start flags>` |
| After an edit, run the code on disk | `npx @expo/agent-cli runtime:reload` |
| What the app threw | `npx @expo/agent-cli runtime:errors` |
| What is on screen, by testID | `npx @expo/agent-cli runtime:tree` |
| Send feedback to Expo | `npx @expo/agent-cli feedback --message "…"` |

Exceptions in this repo:

- Do not run `dev --ios|--android` (except with `--plan`) or
  `smoke --ios|--android`. For this project they start a local
  `expo prebuild` and a local Xcode or Gradle build when no matching local
  build exists, and they use a local device, not the cloud simulator.
- Do not use the `--eas` flags (`dev`, `smoke`, `navigate`,
  `runtime:reload`, `dev:stop`). They drive only `agent-device` sessions and
  pick any live session of the Expo project, so they do not see this
  worktree's argent session and can take another worktree's. The cloud
  simulator session belongs to `eas-sim-dev` (`tools/agent/sim-session.sh`).
- The CI agents in `tools/agent/` keep their fixed tool lists
  (`bun run typecheck`), so a CI run stays reproducible.

## Pull requests: the fork only

- Open pull requests only on the fork `keith-kurak/brooks-expo`, with base
  `main`. Never open a PR, an issue, or a comment on the upstream repository
  `SchroederNathan/brooks-expo`, even when a tool suggests it.
- Push branches to `origin` (the fork) only. The `upstream` remote is for
  fetching.
- Always name the repository, so the PR does not depend on the `gh`
  default:

  ```bash
  git push -u origin HEAD
  gh pr create --repo keith-kurak/brooks-expo --base main --head "$(git branch --show-current)"
  ```

## Testing on a device

- **Default to an EAS cloud iOS simulator.** When a task needs the app on a
  device — to reproduce a bug, check a UI change, or verify a fix — use the
  `eas-sim-dev` skill without asking first. This applies even on a Mac with
  local simulators, and it overrides general device-selection rules (for
  example "prefer a running local simulator"). Use a local simulator or an
  Android emulator only when the user asks for one.
- One cloud iOS simulator per worktree. Stop it when the task is done.
- To show a person the change on iOS and Android, use `eas-sim-preview`.
- See [LLP 0009](./llp/0009-testflight-agent-pipeline.design.md#local-development).
